## Disposable database parity lifecycle

This section is the canonical provider-safety policy for every database-backed source or destination parity cycle. Task 7 of the [operative migration plan](../superpowers/plans/2026-09-06-atmoshaper-repository-migration.md#task-7-verify-and-create-the-fresh-local-atmoshaper-initial-commit) is the sole executable sequence. Each cycle is a one-project lifecycle; prior authorization or a prior successful QA target never permits reuse.

1. Create a fresh empty QA project for that cycle only. Stop if the target already exists, contains application data, or cannot be proved separate from production.
2. Before connecting or applying anything, verify the approved non-production fingerprint through the fail-closed repository gate. Record only pass/fail and the environment role; never record credentials, connection strings, provider/project IDs, or database rows.
3. Apply only the migrations committed in the repository, in order. Do not copy production schema or data and do not run ad hoc DDL or seed real identities.
4. Use synthetic `.example.test` fixtures only through the repository-owned Browser-QA helpers. Keep all ordinary provider writes disabled or mocked/read-only as required by the parity contract.
5. In `finally`-owned cleanup, remove the exact synthetic fixtures and prove zero retained fixture rows in every table the harness can touch. A failed test does not relax cleanup.
6. Delete the disposable project after the cycle, then perform a separate readback proving the project is absent. Preserve only the redacted lifecycle receipt.

Production and every previously used QA project are prohibited parity targets. Missing fingerprint evidence, incomplete migration status, non-synthetic data, failed fixture cleanup, failed deletion, or missing absence proof stops the parity claim and the next migration task.

## Ably staging gate

The locked server reads `ABLY_API_KEY`, publishes compact change events with a three-second timeout, and signs one-hour TokenRequests limited to the normalized room channel with `subscribe` and `presence` capabilities. The browser obtains the local realtime token, loads the Ably SDK, subscribes to that same channel, and wakes its polling owner on a signal; connection/setup failure displays the automatic-refresh fallback. The database remains authoritative. Keep the environment variable, channel normalization, event identifiers and token capability boundary unchanged. Public product naming is not permission to rename these contracts.

Before staging, record which of these two modes is deliberately selected, with source and destination environment roles stated explicitly:

- **Isolated Ably:** separately authorize an isolated non-production app/key configuration, then read back its environment binding, server publishing capability, client subscribe/presence scope and quota/health status without exposing credentials or real room identities. Preserve the existing channel namespace inside the isolated app so identical room codes cannot cross into production. Authorized synthetic connection/authentication/subscription checks must not publish messages or enter/update presence. Use the existing local Ably harness in `tests/browser/anatomime-traffic.spec.ts` to verify signal-triggered refresh and subscription cleanup without sending provider messages; distinguish this mocked signal proof from hosted connectivity evidence.
- **Provider disabled / fallback:** deliberately leave Ably unconfigured in the isolated verification environment, verify the bounded unavailable path and automatic polling, and record that realtime was not exercised. A working polling fallback does not establish enabled-realtime parity. If the source baseline requires configured realtime, keep that parity gate pending until the isolated-Ably checks are complete; do not silently accept the degraded path.

Rollback preserves the prior approved environment-to-app/key binding and restores only that separately authorized binding/configuration if necessary. Do not rename channels, rotate or retire a production key/app, replay events or publish a recovery message. If fallback is the approved temporary rollback mode, record the missing realtime capability explicitly. Provider configuration remains unverified in Task 2; no Ably request, token issuance or publication was performed.
